## 1 需求与交付范围

### 1.1 要实现的功能

调用方只需提供账号与密码，程序自动完成以下动作，无需人工在浏览器中点击：

- 向飞牛音乐服务端发起密码登录，换取访问令牌
- 持令牌调用扫描接口，触发音乐库扫描
- 查询扫描任务状态，反馈进度与结果

本文档提供全部所需的接口路径、请求头、请求体、响应结构、错误码，以及一段可直接运行的参考实现。

### 1.2 基础信息

| 项 | 值 |
|---|---|
| 服务基址 | `http://<NAS_IP>:5666` |
| 接口前缀 | `/music/api/v1` |
| 默认端口 | `5666` |
| 协议 | HTTP（局域网内）；如需公网访问建议自行加 HTTPS 反代 |
| 响应格式 | JSON，统一包裹 `{ code, msg, data }`，`code === 0` 表示成功 |
| 认证方式 | Cookie：`music-token=<userToken>` |

### 1.3 统一响应结构

```json
{
  "code": 0,          // 0 = 成功；非 0 见第 6 节错误码
  "msg":  "",         // 失败时的可读描述
  "data": { ... }     // 业务数据，失败时多为 null
}
```

> **重要提示**
>
> HTTP 状态码与业务码需分别判断：令牌缺失时服务端返回 HTTP 401，同时 body 中 code 为 99999；
> 而参数错误时 HTTP 可能是 200，但 body 中 code 非 0。请以 body.code 为准判断业务结果。

## 2 鉴权机制（实现的核心）

### 2.1 令牌的唯一载体：Cookie music-token

这是本项目最容易踩坑的地方，务必按如下结论实现：

- 服务端认的唯一凭据是 Cookie 中的 music-token，值为登录接口返回的 data.userToken。
- Authorization: Bearer、x-token、userToken 等请求头，以及 URL 查询参数，均不被接受，会返回 401。
- 该 Cookie 由前端 JavaScript 自行写入，服务端登录响应中并不包含 Set-Cookie 指令。

**表 2-1 music-token 的关键属性（已核实）**

| 属性 | 值 | 实现影响 |
|---|---|---|
| 写入方 | 前端 JS（非服务端 Set-Cookie） | curl／程序需手动设置该 Cookie |
| 值 | 登录响应 data.userToken（32 位小写 hex） | 登录后立即取出并复用 |
| 有效期 | 会话级，无 expires | 关浏览器即失效，长期任务需重新登录 |
| HttpOnly | 否 | 可被 JS 读写，故前端能自行管理 |
| SameSite | Strict | 仅同站请求携带 |
| Path | / | 根路径下全部请求携带 |

### 2.2 签发流程

令牌从产生到使用的完整路径：

```text
① POST /user/password-login        （提交账号 + 密码摘要）
        ↓  响应 data.userToken = "3c855ef5...823b"
② 前端 JS 写入 Cookie：
   document.cookie = `music-token=${token}; Path=/; SameSite=Strict`
        ↓
③ 后续所有 /music/api/v1/* 请求自动携带该 Cookie
        ↓
④ 服务端据此识别用户身份与权限（role=admin 才有扫描权限）
```

> **为什么这很关键**
>
> 很多同学会先尝试「登录 → 从响应头找 Token → 塞进 Authorization」，这条路线在本系统上必然失败。
> 正确做法是：把 data.userToken 原样作为 music-token Cookie 的值。
> 另外，桌面客户端（app:// 协议）不写 Cookie，改由原生桥持有会话，因此程序对接请一律走 Web 端接口。

### 2.3 设备标识 deviceId

登录请求体中的 deviceId 用于标识设备，服务端不校验其真实性，实现时按以下任一方式即可：

- 随机生成 16 字节并转 32 位小写 hex（推荐，每次安装固定一个）
- 读取 Web 端已存在的值：localStorage 键名 music-device__id
- 固定填一个常量也可通过（同一设备身份重复使用不会冲突）

### 2.4 请求头 authx 说明

抓包可见每个请求都带有形如 nonce=...&timestamp=...&sign=... 的 authx 请求头。需分两个层面理解：**该头必须存在**，但**其中的 sign 值不被校验**。

> **实测结论：authx 必须携带，值可自行捏造（2026-10-30 修订）**
>
> 1. 已登录接口（`/user/me`、`/shared-library/list`、`/task/list`）在携带合法 Cookie、但**不带 authx** 时，
>    均返回 `{"code":99999,"msg":"INVALID TOKEN"}`；同一时刻同一浏览器内音乐 App 自身请求正常，
>    说明会话有效，被拒的唯一差异项就是缺少 authx。
> 2. 携带 authx 但把 sign 换成任意值（如 32 个 0），接口可正常返回业务数据 ——
>    服务端只校验该请求头**是否存在**，不校验签名正确性。
> 3. 登录接口 `/user/password-login` 是例外：不带 authx 也能成功。
>
> **实现要求**：登录成功后的所有请求都必须携带 authx 头，但无需还原签名算法，值可固定填充。
> 推荐格式：`nonce=6位数字&timestamp=毫秒时间戳&sign=32位hex`（sign 用随机 hex 即可）。
>
> 说明：本文档早期版本曾写「authx 可省略」，该结论经复核已作废，请以本节为准。

## 3 登录接口详解

### 3.1 接口定义

| 项 | 内容 |
|---|---|
| 方法 | `POST` |
| 路径 | `/music/api/v1/user/password-login` |
| Content-Type | `application/json` |
| 是否需要登录 | 否（登录入口） |
| 权限要求 | 无 |

**表 3-1 请求体字段**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| username | string | 是 | 登录用户名，例如 ZERS |
| password | string | 是 | 密码的 SHA-256 摘要，64 位小写 hex（见 3.2） |
| deviceId | string | 是 | 32 位小写 hex 设备标识（见 2.3） |

### 3.2 密码加密规则

页面不会提交明文密码。抓包捕获到的 password 字段为 64 位小写十六进制字符串：

```text
password = "a088d59cb5835040f1d7e3049ebafa8361fd30b9b457f3d7a8db78dd9e8a40b9"
```

**实现方式：**取明文密码做 SHA-256，输出小写 hex，即为提交值。

```python
# Python
import hashlib
password_hash = hashlib.sha256(plain_password.encode('utf-8')).hexdigest()
```

```javascript
// JavaScript（浏览器需 HTTPS 才能用 crypto.subtle）
const buf = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(pwd));
const password_hash = [...new Uint8Array(buf)].map(b => b.toString(16).padStart(2,'0')).join('');
```

> **建议先用 5 分钟自测一次（很重要）**
>
> 已确认的事实：提交值为 64 位小写 hex，且该值被服务端接受、登录成功。
> 尚未直接验证：是否为「无盐 SHA-256(明文)」——因为无法从摘要反推原文。
> 自测方法：用你的账号，分别尝试 SHA-256(明文) 与 MD5(明文) 提交，看哪个返回 code=0。
> 预期为 SHA-256；若失败再试验证是否有固定前后缀（如 sha256(salt + pwd)）。
> 补充：若对接方拿到的是用户端已算好的 64 位密文，可原样透传，不必反推明文，也就不受盐值问题影响。
> 自测脚本见附录 A，改两行即可。

### 4.2 扫描全部音乐库（一键扫描）

**这是「一键扫描」功能的直接实现，无需传任何参数。**

| 项 | 内容 |
|---|---|
| 方法 | `POST` |
| 路径 | `/music/api/v1/shared-library/scan-all` |
| Content-Type | `application/json` |
| 请求体 | `{}`（空对象即可） |
| 成功响应 | `{"code":0,"msg":"","data":null}` |

```bash
curl -X POST 'http://192.168.31.15:5666/music/api/v1/shared-library/scan-all' \
  -H "Cookie: music-token=<userToken>" \
  -H 'Content-Type: application/json' \
  -d '{}'
```

### 4.3 扫描指定单个音乐库

| 项 | 内容 |
|---|---|
| 方法 | `POST` |
| 路径 | `/music/api/v1/shared-library/scan` |
| Content-Type | `application/json` |

curl -X POST 'http://192.168.31.15:5666/music/api/v1/shared-library/scan' \

> **调用注意**

### 4.4 查询扫描进度

扫描是异步任务，提交后接口立即返回，需通过任务列表查询进度。

| 项 | 内容 |
|---|---|
| 方法 | `GET` |
| 路径 | `/music/api/v1/task/list` |
| 筛选 | 取 `data.list[]` 中 `type === "fileScan"` 的项 |

**表 4-2 扫描任务字段**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | string | 任务 ID（UUID） |
| type | string | 固定为 fileScan |
| name | string | 任务名，通常为库目录名 |
| total | number | 待处理文件总数 |
| successCount | number | 已成功入库数量 |
| failCount | number | 失败数量 |
| done | boolean | 是否已完成（true 即扫描结束） |
| canceled / cancelling | boolean | 是否已取消 / 正在取消 |
| retryable | boolean | 是否可重试 |
| createdAt | number | 任务创建时间（Unix 秒） |
| ext.libraryGUID | string | 所属音乐库 guid，可与库列表关联 |

建议轮询间隔 3～5 秒，当所有相关任务的 done 均为 true 时结束轮询并汇总成功/失败数量。

## 5 参考实现

### 5.1 整体流程

```text
输入：NAS 地址、端口、用户名、密码
  │
  ├─1. password_hash = SHA256(明文密码)
  ├─2. POST /user/password-login  → 取 data.userToken
  ├─3. 组装 Cookie: music-token=<userToken>
  ├─4. POST /shared-library/scan-all  → code=0 表示已提交
  ├─5. 轮询 GET /task/list（筛 type=fileScan）
  └─6. 全部 done=true → 输出汇总
```

### 5.2 Python 实现（requests）

```python
import hashlib, random, time, uuid, requests

def make_authx():
    """生成 authx 请求头。

    服务端只校验该头存在，不校验 sign 值；因此 sign 用随机 hex 占位即可。
    已登录接口（user/me、shared-library/*、task/list）缺此头会返回 99999。
    """
    nonce = f"{random.randint(0, 999999):06d}"
    timestamp = int(time.time() * 1000)
    sign = uuid.uuid4().hex                    # 32 位 hex，任意值均可通过
    return {"authx": f"nonce={nonce}&timestamp={timestamp}&sign={sign}"}


class FnMusicClient:
    def __init__(self, host, port=5666, timeout=15):
        self.base = f"http://{host}:{port}/music/api/v1"
        self.host = host
        self.s = requests.Session()
        # 关键：authx 挂到 Session 默认头，登录后的每个请求都会自动携带
        self.s.headers.update(make_authx())
        self.timeout = timeout

    def login(self, username, password):
        pw = hashlib.sha256(password.encode('utf-8')).hexdigest()
        device_id = uuid.uuid4().hex          # 32 位 hex
        r = self.s.post(f"{self.base}/user/password-login", json={
            "username": username,
            "password": pw,
            "deviceId": device_id,
        }, timeout=self.timeout)
        j = r.json()
        if j.get("code") != 0:
            raise RuntimeError(f"登录失败: {j.get('code')} {j.get('msg')}")
        token = j["data"]["userToken"]
        # 关键：把 token 塞进 Cookie，而不是 Authorization 头
        self.s.cookies.set("music-token", token, domain=self.host, path="/")
        return j["data"]["user"]

    def list_libraries(self):
        j = self.s.get(f"{self.base}/shared-library/list", timeout=self.timeout).json()
        return j["data"]["list"]

    def scan_all(self):
        j = self.s.post(f"{self.base}/shared-library/scan-all", json={},
                        timeout=self.timeout).json()
        return j.get("code") == 0

    def scan_one(self, guid):
        j = self.s.post(f"{self.base}/shared-library/scan",
                        json={"guid": guid}, timeout=self.timeout).json()
        return j.get("code") == 0

    def scan_tasks(self):
        j = self.s.get(f"{self.base}/task/list", timeout=self.timeout).json()
        return [t for t in (j.get("data") or {}).get("list", [])
                if t.get("type") == "fileScan"]

    def wait_scan_done(self, interval=4, max_wait=3600):
        start = time.time()
        while time.time() - start < max_wait:
            tasks = self.scan_tasks()
            if tasks and all(t.get("done") for t in tasks):
                return tasks
            time.sleep(interval)
        return self.scan_tasks()

if __name__ == "__main__":
    c = FnMusicClient("192.168.31.15")
    user = c.login("你的用户名", "你的密码")
    print("登录成功:", user["name"], user["role"])
    print("音乐库数量:", len(c.list_libraries()))
    if c.scan_all():
        print("扫描任务已提交，等待完成...")
        for t in c.wait_scan_done():
            print(f"  {t['name']}: {t['successCount']}/{t['total']} fail={t['failCount']}")
```

### 5.3 关键实现要点

- 必须用 Session 保持 Cookie：token 走 Cookie，不是请求头，用 curl 时写 -H "Cookie: music-token=..."。
- password 提交的是摘要不是明文，忘记哈希会返回登录失败。
- authx 头**必须携带**：已登录接口缺它一律返回 99999；但 sign 值不校验，填 32 位随机 hex 即可，无需实现签名算法。
- HTTP 401 通常意味着 Cookie 没带或 token 已失效（会话级，重启浏览器后失效）。
- scan-all 提交成功只代表任务已入队，必须轮询 task/list 才能确认扫描真正完成。

## 6 错误码与排错

**表 6-1 实测错误码**

| code | HTTP | 含义 | 处理建议 |
|---|---|---|---|
| 0 | 200 | 成功 | 正常继续 |
| 99999 | 401 | 令牌缺失或无效（INVALID TOKEN） | 检查 Cookie 是否携带、**authx 头是否携带**、token 是否过期 |
| 120001 | 401 | 用户名或密码错误（unauthorized） | 核对账号密码；确认 password 已做 SHA-256 后再提交 |
| 100001 | 200 | 参数错误（如 scan 未传 guid） | 补齐必填参数 |
| 100005 | 200 | 资源不存在（resource not found） | guid 有误或音乐库已被删除，重新拉取列表 |

### 6.1 常见问题

- 返回 401 但确认已登录：Cookie 可能被放在了请求头 Authorization 中；本系统只认 Cookie。
- 登录返回非 0：检查 password 是否已 SHA-256；检查 username 大小写。
- scan 返回 100005：guid 抄错，先用 shared-library/list 取真实 guid。
- 提交扫描后无进度：确认任务是异步的，去 task/list 看 fileScan 项；total=0 表示该库无可扫描音频。
- 扫描权限不足：检查登录用户的 role 是否为 admin。

## 7 安全与合规要求

- music-token 等同于账号会话，请勿写入日志、URL 或前端明文配置；建议加密存储于服务端。
- 密码只在内存中做 SHA-256，不落盘、不打日志。
- 生产环境建议通过 HTTPS 反向代理访问，避免明文传输。
- 扫描会遍历存储，对网盘挂载路径可能产生较大流量与耗时，建议加确认步骤与频率限制。
- 本方案基于对自有设备的接口分析，请仅用于自有系统集成，遵守目标系统的使用条款。

### B.1 关于第 4 项的复核细节

复核方法：在已登录浏览器中直接访问接口地址（同站导航，浏览器自动携带 Cookie，但绝不会附加自定义 authx 头）。

| 请求 | 携带 Cookie | 携带 authx | 返回 |
|---|---|---|---|
| GET /user/me | 是 | 否 | `{"code":99999,"msg":"INVALID TOKEN"}` |
| GET /shared-library/list | 是 | 否 | `{"code":99999,"msg":"INVALID TOKEN"}` |
| GET /task/list | 是 | 否 | `{"code":99999,"msg":"INVALID TOKEN"}` |

对照：同一时刻打开音乐 App 主界面，页面数据正常加载，证明会话有效、Cookie 有效。
故结论为 **authx 参与鉴权存在性校验**，旧版「可省略」判断错误，已作废。

### B.2 对实现方的直接影响

- 所有登录后请求（拉库列表、扫描、查任务）都必须带 authx，否则 99999。
- authx 的值不必与浏览器一致，随机生成即可，无需逆向签名密钥。
- 排错顺序建议：先查 Cookie 有无 → 再查 authx 有无 → 最后才怀疑 token 过期。
